Extension rules
===============

Discovery
---------
Extensions are discovered in child directories that contain an `extension.json` manifest. Directories without a manifest are ignored. The loader checks these roots in order:
  1. <application-base-directory>/extensions
  2. %LocalAppData%/LaunchPad.Ignite/extensions

Directories within each root are enumerated in case-insensitive path order. Missing roots are ignored. If manifests use the same `id` (case-insensitively), the manifest encountered later replaces the earlier one; therefore a matching user extension replaces the app-installed extension.

Manifest
--------
Each extension directory contains one `extension.json` file with this shape:

{
  "id": "example",
  "name": "Example Extension",
  "namespace": "example",
  "schema": {
	"variables": [],
	"lists": [],
	"commands": [],
	"functions": []
  },
  "assembly": "Example.Extension.dll"
}

`id`, `name`, `namespace`, and `schema` are required. `id`, `name`, and `namespace` must be non-empty strings. `schema` must contain `lists` and `commands` arrays; `variables` and `functions` are optional and default to empty arrays. Use the supported schema fields and rules described in `rules-parser.txt` and `rules-function.txt`. `assembly` is optional. JSON property names are case-insensitive, and enum values such as execution mode and list mode use camel-case strings.

Namespacing
-----------
The manifest's `namespace` is assigned to every command and variable in the extension schema, replacing any namespace present on those entries. Lists are shared by type and name and do not receive a namespace.

Invoke a namespaced command as `namespace:command`; command and namespace lookup is case-insensitive. Refer to an extension variable in a URL target as `$namespace:variable`. A command name or variable name must not contain `:`; namespaces must not contain `:`.

Schema and validation
---------------------
- Extension command definitions use the same `CommandDefinition` schema as app and user commands. Actions must define `targetTemplate` and at least one action must be present.
- Lists currently support only `type: "enum"`. List names are unique per type, values must be non-empty, and values must be unique case-insensitively. Reference a list from an argument with `"ref": "enum:listName"`.
- Variables require a non-empty value and unique qualified name.
- Argument and execution fields, including `arguments`, `optional`, `ref`, `inputType`, `allowCustomValues`, `listMode`, `targetTemplate`, and `execution`, follow `rules-parser.txt`.
- A command `kind` must be `url`, the built-in `shortcut` kind, or match a loaded extension executor's `Kind`, case-insensitively.
- Extension command kinds are open-ended: any non-empty `ICommandExecutor.Kind` may be supplied by an extension; they are not restricted to a built-in list.
- Schema validation errors prevent the command catalog from being created; malformed manifests and invalid executor assemblies also fail extension loading.

Executors
---------
An extension may omit `assembly` when it only defines schema commands and generic HTTP/script functions. When `assembly` is supplied, it must resolve to a file inside that extension's directory and must exist. The assembly must contain at least one concrete `ICommandExecutor` or `IExtensionFunctionExecutor`. Each executor must have a public parameterless constructor. Command executor kinds must be non-empty and unique across loaded extensions. The `url` kind is provided by the host and cannot be registered by an extension.

An `IExtensionFunctionExecutor` declares an unqualified `FunctionName`; the loader prefixes the extension manifest namespace and requires a matching `schema.functions` entry with no generic execution `kind`. Conversely, a function entry with no `kind` must have exactly one matching extension function executor. Function handlers and command executors may coexist in one assembly.

User overrides
--------------
After extensions load, `%LocalAppData%/LaunchPad.Ignite/user-commands.json` is merged over the app and extension schema. A user command replaces the command with the same qualified name; a user list replaces a list with the same type and name; a user variable replaces the variable with the same qualified name. Comparisons are case-insensitive. User-defined command namespaces are used as supplied rather than assigned from an extension manifest.

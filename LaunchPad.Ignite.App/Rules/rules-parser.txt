Command and parser rules
========================

Notation
--------
  <arg> = required argument
  [arg] = optional argument
  /value/ = ghost-text completion preview; it is not committed input
  {key} = key press

Input and parsing
-----------------
- Input is tokenized on whitespace. Quoting and escaping are not supported; a value cannot contain whitespace.
- Command and action lookup is case-insensitive. A namespaced command is written `namespace:command`; an unnamespaced command uses its name alone.
- A command may have a `default` action. Otherwise an action name is required before its arguments. The action name is omitted from the syntax for the default action.
- Arguments are strings by default and required unless `optional` is true. Required arguments must precede optional arguments in the schema.
- Arguments can be positional, named as `name=value`, or mixed. Names are case-insensitive; positional values fill the next argument not already assigned. Unknown, duplicate, and empty named values are invalid. Any token containing `=` is interpreted as a named argument, so positional values containing `=` are not supported.
- Missing required arguments produce an incomplete parse. Invalid commands or values produce an invalid parse. Optional arguments omitted from input are absent from the parsed argument map.
- `inputType` currently supports only `csv`. CSV values remain a string during parsing and cannot be empty or contain empty comma-delimited entries.
- An argument with `ref: "enum:name"` is checked against the matching declared enum values, case-insensitively. `allowCustomValues: true` permits other non-empty values during parsing, but completion suggestions still come only from the declared enum values.
- `ref: "list:name"` represents a multi-value list supplied by an argument value provider. List values are comma-delimited and must be non-empty, valid, and unique. The current application does not configure a dynamic list provider, so it does not supply values for these references.

Schema basics
-------------
Command definitions are held in a schema with `lists`, `variables`, and `commands` arrays. App definitions are combined with extension definitions, then `%LocalAppData%/LaunchPad.Ignite/user-commands.json` is merged over them. A user command replaces one with the same qualified name; a user list replaces one with the same type and name; a user variable replaces one with the same qualified name. Comparisons are case-insensitive. The user schema file is created empty on first run.

Lists currently support only `type: "enum"`; each list needs a name and non-empty, case-insensitively unique values. Reference it with `ref: "enum:listName"`.

Each command must declare at least one action, and every action must define a non-empty `targetTemplate`. Variables require a non-empty value and may be unqualified or use a namespace; refer to them as `$variable` or `$namespace:variable`. Use `variable set <name> <value>` to create or update a persistent user variable and `variable remove <name>` to remove one.
Use `settings` to open Settings, `import-export` to open profile import/export, and `help` to open the help screen. `Ctrl+.` opens Settings, `Ctrl+I` opens Import/Export, and `Ctrl+H` opens Help.

Use `mode toggle` to switch between the main and mini launcher windows, `mode main` to show the full results list, and `mode mini` to show the compact launcher. `Ctrl+M` toggles between the two modes. Mini mode shows the LaunchPad rocket mark and lock/settings controls; its lock button uses the same master-password flow as `secret lock` and `secret unlock`. The mini status shows the current completion and its position while typing, then shows command usage when an exact command is followed by whitespace.

The `app:keepWindowOpen` general setting controls whether the launcher stays visible when it loses focus during command execution. It defaults to `Off`, which preserves the normal hide-on-deactivation behavior.

The built-in `shortcut` kind defines an alias and optional keyboard chord. It must have one `default` action with no arguments or execution; its `targetTemplate` is the command text to expand to. Use `launchpad command add shortcut <name> --target "<command text>" [--key <chord>] [--description <text>]` to create a user shortcut, for example `launchpad command add shortcut wx --target "weather forecast" --key ctrl+alt+w`. Shortcut key chords use a modifier and key separated by `+`; supported modifiers are `ctrl`, `alt`, `shift`, and `meta`, and keys may be letters, digits, or `num+<digit>`.

Use `launchpad command edit <name> [--target <command text>] [--key <chord>|--clear-key] [--description <text>]` to edit a user shortcut. `--key` assigns a chord that immediately executes the shortcut target; `--clear-key` removes only the chord. The two key options cannot be combined and are supported only for shortcut commands. Use `launchpad command remove <name>` to remove the whole user command or shortcut alias. Shortcut names may be namespaced as `namespace:name`.

Arguments use the `arguments` property (not `args`). Supported argument properties are `name`, `optional`, `ref`, `inputType`, `listMode`, and `allowCustomValues`. Supported `inputType` is `csv`. `listMode` is `normal` or `minimal` and applies to checklist-style `list:` references.

Completion behavior
-------------------
- Command, action, and enum candidates are filtered by the typed prefix without regard to case. No candidates are shown if none match.
- A leading `&` filters shortcut aliases by prefix. {right} or {tab} replaces the filter with the selected alias text only, not its expanded command (for example, selecting `[pl:arch]` from `&pl:arch` inserts `pl:arch`).
- A leading `>` enters command metadata filter input and suggests `kind`, `pack`, and `extension`. {right} or {tab} accepts a field and inserts its trailing `:` (for example, `>kind:`). `kind` is the user-facing command category (`url`, `shell`, `shortcut`, `variable`, `secret`, `snippet`, or `system`); `handler` identifies the execution route and is separate from filtering. Use `kind:<kind>`, `pack:<packId>`, and/or `extension:<extensionId>`, separated by commas (for example, `>kind:url` or `>extension:ado,kind:system`). The filter stays visible in the command input, while only the command text after it is used for execution and history. Matching values appear as selectable candidates; {up}/{down} changes selection and {tab} or {space} accepts a value. Type a space after the filter to continue with command text. The active filter persists for the current launcher session, limits command suggestions only, and command ghost text appears after the visible filter prefix.
- Direct UNC path completion suggests network shares after `\\server\` and matching files or folders inside a selected share.
- {right} accepts filesystem path suggestions one directory segment at a time, including the segment's trailing separator.
- For a selected command-history suggestion, {right} accepts one whitespace-delimited command token at a time, while {tab} accepts the complete command. The `[history]` display label is never inserted into command input. A selected history item remains visible alongside the file/folder picker; filesystem picker suggestions continue to accept one path segment at a time with {right}.
- A leading `^` filters stored snippet names by prefix. {right} or {tab} replaces the filter with `snippet run <name>`; {enter} then runs that command.
- {shift+up} and {shift+down} move the completion-list highlight to the top and bottom. {alt+up} and {alt+down} cycle matching history suggestions without replacing the typed text: {alt+up} moves toward older entries and {alt+down} toward newer entries. {alt+home} selects the most recent matching history entry; {alt+end} selects the oldest. Ghost text and the highlighted history item follow the selected entry.
- Completion resolves argument position by token position; it does not account for already supplied `name=value` arguments. Named arguments are supported by the parser, but completion after named arguments may not reflect the parser's next unassigned argument.
- {up} and {down} move the highlight through candidates and wrap at either end. {tab} accepts a regular command, action, or enum candidate. A space is appended after acceptance only when the completion engine determines a following required argument needs one; it does not add a space before an optional next argument.
- For a normal-mode `list:` checklist, {tab} toggles the highlighted value. Checked values remain visible, values are comma-delimited in the command line, and no trailing comma is added. {ctrl+a} selects all values and {ctrl+d} clears them, including values not currently visible due to filtering.
- For a `list:` checklist with `listMode: "minimal"`, {tab} accepts the highlighted value, adds it to the committed comma-delimited selections, and removes it from the remaining choices. The list remains available for further selection.
- Typing filters checklist values by prefix. The highlighted candidate's unmatched suffix is shown as ghost text. Ghost text is only a preview: {enter} does not commit it.
- In checklist mode, {space} advances to the next argument only when at least one value is selected and a next argument exists. It does not select ghost text. Otherwise it does not advance.
- {enter} parses and executes only committed input. On success, the command box is cleared and the launcher remains open. Incomplete, invalid, or unsuccessful commands remain open with their input intact. {esc} clears the command and closes the launcher. {ctrl+backspace} clears the command and leaves the launcher open.

URL execution
-------------
- A `kind: "url"` command action requires a non-empty `targetTemplate`. `<argumentName>` placeholders are replaced by parsed argument values; values are URI-escaped. Missing optional placeholder values become empty strings, and empty query parameters are removed.
- `$variable` and `$namespace:variable` references in URL targets are replaced by the matching schema variable. Unknown placeholders or variables, or targets that are not absolute HTTP/HTTPS URLs, fail target construction.
- An action may declare `execution: { "mode": "targetPerValue", "arguments": ["csvArgument"] }`. Each named argument must exist and have `inputType: "csv"`. The URL executor builds a target for each value; multiple target-per-value arguments produce the cartesian product of their values.
- Other command kinds are dispatched to a registered `ICommandExecutor`; extension loading and executor rules are in `rules-extension.txt`.

Value printing
--------------
- A line beginning with `?` followed by whitespace evaluates and displays the remaining text. Variables and functions are expanded before the value is shown in the status area.
- Examples: `? x`, `? $project`, `? @namespace:functionName(argument)`.
- A successful value print clears the command input. An empty expression or expansion error leaves the input in place and displays an error.

Current ADO extension examples
------------------------------
The ADO extension declares the `ado` namespace and a `project` enum. These inputs are valid:
  ado:pipeline claims
  ado:pipeline project=claims pipelineId=1234
  ado:pipeline claims 1234,2345
  ado:repo claims repoName=LaunchPad.Ignite

The `pipelineId` and `repoName` arguments are optional CSV strings configured for `targetPerValue` execution. The `project` argument allows custom enum values: custom values parse successfully, although they are not suggested by completion.

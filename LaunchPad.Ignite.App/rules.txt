Legend:
  <arg> = required
  [arg] = optional
  /value/ = ghost text
  {key} = key press
  {enter} = execute the current committed command if it is valid; never accept ghost text. After successful execution, clear the command box and close the launcher. Invalid, incomplete, or failed commands leave the input and window open.
  {tab} = accept/complete command or argument
  {space} = activates the next argument. If that argument is a list, it enters checklist mode. The system may append a space automatically after an argument is completed when the next argument is required. It does not append a space automatically when the next argument is optional.
  {ctrl+backspace} = cancels command entirely. clears command and keeps window open
  {esc} = cancel command entirely. clears command and closes window

  <list:source> = multi-value checklist populated by source. Source is either a named list or the reserved source "secrets".
  An argument with "ref": "list:secret" uses the reserved "secrets" source.
  <enum:name> selects one value from the named enum list; <list:name> selects one or more values from that list. Enum arguments reject values outside the enum by default; an argument with "allowCustomValues": true also accepts a non-empty value not listed in the enum.
  <flag:name> selects one boolean value and is not a multi-value checklist.
  <csv:name> = comma-delimited text input retained as a string; it does not open a checklist. Use [csv:name] for an optional argument. An execution mode may split this string when iterating over values.
  Arguments are strings by default. A "ref" property binds an argument to a named list and determines its available choices; input metadata such as CSV changes input handling, not the argument's string type.
  An execution mode of "targetPerValue" creates one target for each comma-delimited value in the named CSV string argument.

  Command suggestions are filtered case-insensitively by the typed prefix; show no command suggestions when nothing matches. Enum completion suggestions remain limited to declared options, even when the argument allows manually entered custom values.
  A command may declare a "namespace". Invoke it as namespace:commandname; unnamespaced commands keep their current syntax. Namespace and command-name matching is case-insensitive.
  Arguments may be supplied by name as argName=value for required or optional arguments. Named and positional values may be mixed; positional values fill the next argument not already assigned. Argument names are case-insensitive. Unknown, duplicate, or empty named values are invalid.

  Checklist behavior:
  - The checklist is kept open until the user presses {enter} to execute using committed selections, {esc} to cancel the command, or {space} to exit checklist mode and continue typing the next argument.
  - {space} does not select ghost text. It exits checklist mode and advances to the next argument. If there is no next argument, use {enter} to execute or {esc} to cancel.
  - The first available item is highlighted when the checklist opens and shown in ghost text.
  - When a user types, the list is filtered to items that start with the typed text. The first available item is highlighted and the text remainder is shown in ghost text.
  - While a checklist is active, checklist-specific {tab} behavior takes precedence over the general completion behavior above.
  - Checklist selections are shown comma-delimited in the command line. No trailing comma is added.
  - No argument-separating space is appended automatically while checklist mode is active since we can select multiple items. When the user adds a space, it is interpreted as the end of the checklist argument and the start of the next argument begins.
  - Ghost text is only a preview until accepted with {tab}. Pressing {enter} never accepts ghost text; it executes using only committed command-line values if the command is valid.

  Checklist normal mode:
  - {up} and {down} move the highlight through the available items.
  - Checked items remain in the list and are visibly marked so they can be unchecked.
  - {tab} toggles the highlighted item and changes ghost text. Checked items are included in the command line; unchecked items are removed (no space or trailing comma).
  - {enter} executes using checked items only; it does not check the highlighted ghost item.
  - {ctrl+a} checks all items in the source, including items hidden by filtering, and includes them in the command line.
  - {ctrl+d} unchecks all items and removes them from the command line, including checked items hidden by filtering.

  Checklist minimal mode:
  - The first available item is shown as ghost text.
    Example: "secret shell{space}" -> "secret shell /token1/"
  - {tab} accepts the ghost item, adds it to the command line, removes it from the available ghost options, and shows the next available item as ghost text.
    Example: "secret shell{space}" -> "secret shell /token1/"; {tab} -> "secret shell token1/,token2/"; {down} -> "secret shell token1/,token3/"
  - {enter} executes using accepted items only; it does not accept the visible ghost item.
  - {up} and {down} move through the available ghost options.

Flag list: a list containing the values true and false.
  Usage syntax: <flag:name>
  Schema syntax:
  {
    "type": "flag",
    "name": "name"
  }

Enum list: a static list of values defined in the schema.
  Usage syntax: <enum:name>
  Ex: secret <enum:secret_action>
  Schema syntax:
  {
    "type": "enum",
    "name": "name",
    "source": "user",
    "values": ["value1", "value2", "value3"]
  }
  The source may be "app", "ext", or "user"; it defaults to "user".

Secrets list: the reserved source "secrets" provides the names of secrets stored for the user.
  Usage syntax: <list:secrets>. 
  Ex: secret shell <list:secrets>
  Schema syntax:
  {
    "type": "list:secret",
    "name": "secrets"
  }

Command JSON sources:
  App-provided command definitions are authored in code.
  User-defined command definitions are stored in %LocalAppData%/LaunchPad.Ignite/user-commands.json; an empty file is created on first run.
  The user file uses one CommandSchema object with "lists" and "commands" arrays. A user command replaces an app-provided command with the same name, case-insensitively. User lists replace app lists with the same type and name.
  The command "kind" selects an ICommandModel execution handler. URL target construction and opening belong to UrlCommandModel, not the view model or JSON loader.

Commands:
The example below illustrates the command schema; the built-in pipeline command is defined in code. User-defined commands use the same "commands" array shape in user-commands.json. An action named "default" is implicit and does not appear in the usage string.
[
    {
      "name": "pipeline",
      "kind": "url",
      "description": "Launch ADO pipeline urls",      
      "actions": [
        {
          "name": "default",
          "description": "ADO project",
          "usage": "pipeline <enum:project> [csv:pipelineId]",
          "targetTemplate": "https://dev.azure.com/saifcorporation/<project>/_build?definitionId=<pipelineId>",
          "execution": {
            "mode": "targetPerValue",
            "arguments": ["pipelineId"]
          },
          "arguments": [
            {
              "name": "project",
              "ref": "enum:project",
              "allowCustomValues": true
            },
            {
              "name": "pipelineId",
              "inputType": "csv",
              "optional": true
            }
          ]
        }
      ]
    },
    {
      "name": "secret",
      "kind": "shell",
      "description": "Manage secrets",
      "actions": [
        {
          "name": "shell",
          "description": "Opens a PowerShell terminal with secrets loaded in environment variables",
          "handler": "secrets.openShell",
          "usage": "secret shell <list:secrets> [path]",
          "args": [
            {
              "name": "secrets",
              "ref": "list:secret"
            },
            {
              "name": "path",
              "optional": true
            }
          ]
        },
        {
          "name": "set",
          "description": "Sets a secret value",
          "usage": "secret set <name> [value]",
          "args": [
            {
              "name": "name"
            },

Arguments are strings unless they declare a list reference or input format. Arguments are required unless "optional" is true. When "secret set" is invoked without the optional value, its handler prompts for the value. The "secrets.openShell" handler resolves the selected secret values securely, starts PowerShell with those values in its environment, and uses the optional path as its working directory.

  

1) Command parser and completion acceptance scenario:

Note: This uses the `secret` command only as an example of generic schema-driven parsing and completion.
Apply the same expansion, acceptance, spacing, and multi-value selection rules to any
command whose JSON argument schema declares the corresponding behavior; do not add
command-specific logic to reproduce this scenario.

Secret action syntax relevant to this scenario:
  secret shell <list:secrets>
  secret set <name> [value]
  secret remove <name>

<list:secrets> values are existing secret names. For shell, one or more names are accepted;
multiple names can be supplied as comma-delimited values. [value] is optional inline
for set: when omitted, LaunchPad prompts for the secret value.

Completion expectations:
  type "se" -> "se/cret/"; /cret/ is highlighted ghost text and no space is appended
  press {tab} -> "secret "; the required action/type suggestions are shown
  type "sh" -> "secret sh/ell/"; /ell/ is highlighted ghost text and no space is appended
  press {tab} -> "secret shell "; the required token suggestions are shown
  press {tab} -> "secret shell token1"; token1 is checked, no trailing space is added, and the multi-value token list stays visible
  press {down}, then {tab} -> "secret shell token1,token2"; token2 is also checked, no trailing space is added, and the list stays visible
  press {tab} -> "secret shell token1"; token2 is unchecked and removed, no trailing space is added, and the list stays visible
  press {tab} -> "secret shell token1,token2"; token2 is checked and added, no trailing space is added, and the list stays visible

Parser acceptance examples:
  pipeline x 1234 (x is accepted because the project argument enables custom enum values)
  pipeline project=claims pipelineId=1234
  pipeline project=claims 1234 (the positional value fills the next unassigned argument)
  ns:commandname argName=value (for a command whose schema declares namespace "ns")
  secret shell token1
  secret shell token1,token2
  secret set API_TOKEN
  secret set API_TOKEN actual-value
  secret remove API_TOKEN

   # set $project = architecture

   type "l" -> "pipeline cl/aims/"; filters to arguments that start with cl and the first one is ghost suggested

   plc{tab} -> "pipeline $project"
   # execute command
   plc{enter} -> "pipeline architecture" -> executes the pipeline command with architecture as the project argument.
